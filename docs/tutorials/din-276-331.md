# Tutorial: DIN 276 KG 331 wall

This tutorial follows the checked, non-production fixture in
[`examples/din-276-331`](https://github.com/axioval/schema/tree/main/examples/din-276-331).
It demonstrates the complete path from reusable vocabulary to concrete rules.

!!! warning "Scope and normative sources"
    This is an interchange-modeling example, not legal or standards advice.
    DIN Media identifies
    [DIN 276:2018-12](https://www.dinmedia.de/de/norm/din-276/293154016)
    as *Kosten im Bauwesen*. Public secondary summaries such as
    [WEKA's cost-group table](https://www.weka.de/architekten-ingenieure/kostengruppe-300/)
    label group 331 “Tragende Außenwände.” Use the licensed standard and your
    project's classification specification for production requirements.

## Requirement decomposition

For every object classified with system `DIN 276:2018-12`, code `331`, require:

| Requirement | Reusable concept | Concrete expected value |
| --- | --- | --- |
| Object is a wall | IFC object type `IfcWall` | type match, subtypes accepted |
| Object is load bearing | IFC property `LoadBearing` | boolean `true`, in `Pset_WallCommon` |
| Object is external | IFC property `IsExternal` | boolean `true`, any container |

The official IFC 4.3.2 documentation confirms that
[`Pset_WallCommon`](https://ifc43-docs.standards.buildingsmart.org/IFC/RELEASE/IFC4x3/HTML/lexical/Pset_WallCommon.htm)
applies to walls and defines `LoadBearing` and `IsExternal` as boolean
single-value properties. It defines
[`LoadBearing`](https://ifc43-docs.standards.buildingsmart.org/IFC/RELEASE/IFC4x3/HTML/property/LoadBearing.htm)
as whether an object is intended to carry loads.

## Step 1 — define reusable object and property concepts

The definition package maps stable Axioval IDs to external IFC names:

```pkl
objectTypes {
  ["axioval:example.ifc.wall"] = new Definitions.ObjectTypeDefinition {
    id = "axioval:example.ifc.wall"
    name = new Types.LocalizedText { default = "Wall" }
    externalNames {
      new Definitions.ExternalName {
        typeSystem = "https://identifier.buildingsmart.org/uri/buildingsmart/ifc/4.3"
        name = "IfcWall"
      }
    }
  }
}

properties {
  ["axioval:example.ifc.load-bearing"] = new Definitions.PropertyDefinition {
    id = "axioval:example.ifc.load-bearing"
    name = new Types.LocalizedText { default = "Load bearing" }
    valueKind = "boolean"
    externalNames {
      new Definitions.ExternalName {
        typeSystem = "https://identifier.buildingsmart.org/uri/buildingsmart/ifc/4.3"
        name = "LoadBearing"
      }
    }
  }
}
```

`Pset_WallCommon` is defined separately as a reusable container qualifier. It
does not own either property.

## Step 2 — define typed templates

The example declares two templates:

- `entity-type-equals` takes an `objectTypeReference`; and
- `boolean-property-equals` takes a `propertyReference` constrained by
  `referencedValueKind = "boolean"`, plus a boolean expected value.

A template names a stable application capability. It does not ship executable
checking code.

## Step 3 — scope by classification, not by the desired result

```pkl
local kg331Objects = new Selectors.ClassificationSelector {
  system = "DIN 276:2018-12"
  code = "331"
  includeDescendants = false
}
```

This detail matters. If applicability selected `IfcWall AND KG 331`, a wrongly
classified `IfcSlab` would escape the rule. Classification-only applicability
ensures the separate object-type rule can report it.

## Step 4 — instantiate the object-type requirement

```pkl
new RuleSets.RuleInstance {
  id = "kg331-is-wall"
  definitionId = "axioval:example.entity-type-equals"
  name = new Types.LocalizedText { default = "KG 331 objects are walls" }
  parameters {
    ["objectType"] = new Values.ObjectTypeReferenceValue {
      objectType = "axioval:example.ifc.wall"
      includeSubtypes = true
    }
  }
  applicability = kg331Objects
}
```

## Step 5 — choose strict and loose property references

=== "LoadBearing: strict container"

    ```pkl
    ["property"] = new Values.PropertyReferenceValue {
      property = "axioval:example.ifc.load-bearing"
      propertySet = "axioval:example.ifc.pset-wall-common"
    }
    ["expected"] = new Values.BooleanValue { value = true }
    ```

    A `LoadBearing` property in another set does not satisfy this rule.

=== "IsExternal: container-agnostic"

    ```pkl
    ["property"] = new Values.PropertyReferenceValue {
      property = "axioval:example.ifc.is-external"
    }
    ["expected"] = new Values.BooleanValue { value = true }
    ```

    The adapter still traverses an IFC property-set relationship, but the
    container's identity is not part of this requirement.

## Step 6 — validate source and normalized snapshots

```bash
PATH="$HOME/.local/bin:$PATH" ./scripts/check.sh
```

The gate statically validates `axioval.json`, resolves every declared module
before evaluation, evaluates under the package root, binds all IDs and typed
values, and compares the result with `expected/*.json`.

A registry may cache that normalized output. It must not trust evaluator output
that has skipped binding.

## What a checking application implements

An application adapter must:

1. resolve each `ExternalName` in the active model schema;
2. retrieve classification references and property relationships;
3. distinguish missing, conflicting, invalid, and resolved facts;
4. implement the declared capabilities; and
5. emit stable diagnostics for each failed rule instance.

Axioval standardizes the package data boundary; it does not pretend those engine
semantics disappear.
